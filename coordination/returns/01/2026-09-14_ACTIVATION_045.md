## Direct code-level research findings

### Exact store strengths

`FilesystemObjectStore.load()` / `load_bytes()` already provide a strong exact immutable load primitive once runtime support is available:

- exact ref parsing;
- one exact content-addressed path;
- strict JSON parsing;
- schema validation;
- canonical-byte reproduction;
- exact requested-reference reproduction;
- no logical-id/newest/locator/recency fallback.

### Runtime-support ordering problem

`FilesystemObjectStore._verify_existing()` reads the exact object path **before** schema validation.

That means a Decision 020-valid canonical target kind that is unsupported by the current runtime can produce different store exceptions depending on target-path state before the runtime has established its capability to interpret that kind:

- absent exact path → `ObjectNotFoundError`;
- present bytes followed by missing/invalid inferred schema → the contract failure is wrapped as `ObjectCorruptionError`.

Those outcomes cannot safely become source availability/corruption facts because runtime interpretation capability is a separate truth dimension.

### Mutable observation-context problem

The current store is configured by a filesystem root `Path`. That path is a locator for mutable live state, not an immutable snapshot identity. The same root can yield different exact-target results over time.

Therefore an exact target observer cannot truthfully call the path alone a replayable context.

A useful separation is now durable:

- **institutional replay** may later consume an immutable historical observation record as an input fact;
- **observation re-execution** means reproducing the original live source/store context and rerunning the observation.

The first does not imply the second. Decision 021 must not launder one into the other.
