## Material preflight finding

Code inspection exposed one interpretation-coherence gap that needed to be made explicit before implementation.

Decision 022 classifies runtime capability against the fixed bundled kernel schema directory. `FilesystemObjectStore`, however, can be constructed with an optional caller-supplied `schema_dir`. Its `load_bytes()` uses the store's configured schema context when validating an exact target.

Without an explicit guard, a Decision 023 implementation could therefore do this:

```text
Decision 022 capability fact
    -> target kind is "supported" under bundled schemas
    -> caller supplies FilesystemObjectStore(schema_dir=custom)
    -> exact target bytes are validated under custom schemas
    -> observation fact is emitted as if one coherent runtime interpretation was used
```

That would silently combine two different interpretation contexts. The exact object ref would still be exact, but the institutional claim about what runtime contract was used to interpret it would be ambiguous. A custom schema could reject bytes accepted by the bundled contract, accept a different contract shape, or otherwise change the observed classification without that context being represented in the Decision 023 fact.

This is not a reason to broaden Decision 023 into schema-context identity machinery. The smallest root-grounded repair is the opposite: keep the first slice bounded to the same bundled schema interpretation context already established by Decision 022 and reject custom-schema stores before target-object I/O.
