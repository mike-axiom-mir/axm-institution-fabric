## Decision 021 preliminary research observations

A first code-level inventory was performed before opening any implementation lane.

### Existing exact store primitive

`FilesystemObjectStore.load(reference, schema_name=None)` and `load_bytes(...)` already:

- parse the exact immutable reference;
- infer schema name as `<reference kind>.schema.json` when none is supplied;
- compute the exact content-addressed object path from the immutable reference;
- read only that path;
- strict-parse JSON;
- validate against the chosen kernel schema;
- reproduce canonical bytes;
- reproduce the exact requested immutable reference;
- fail rather than falling back by logical id, version recency, newest object, locator, or store order.

The store has explicit `ObjectNotFoundError`, `ObjectCorruptionError`, `ObjectReferenceMismatchError`, and generic `ObjectStoreError` categories.

### Important unresolved observation-design issue

Decision 020 `exact_axm_object` syntax validation deliberately accepts any canonical AXM immutable reference kind and does not exact-load it.

The current store infers `<kind>.schema.json`. If a declared canonical kind has no schema in the local runtime, a future exact-source observation layer must not casually report that situation as ordinary source corruption or trust failure. Runtime capability/configuration support is a different truth dimension from whether authored source bytes are corrupt.

Similarly, `ObjectNotFoundError` currently means the exact content-addressed path was not present in the inspected store. It does not mean the source never existed globally or is invalid.

This is why Decision 021 remains research-only. A truthful observation result needs an explicit bounded context and must decide how to preserve at least missing, corrupt, unreadable, and unsupported-runtime cases without turning any of them into trust/closure/acceptance policy.

### Leading candidate, still not authorized

The smallest likely later executable slice remains a read-only projection for Decision 020 `exact_axm_object` declarations only, anchored by:

`exact containing object identity + declaration key + exact authored object_ref + explicit inspected store/context identity`

Other source classes would remain explicitly unobserved in that first slice. Exact-load success would remain only an observation fact, not provenance causality, trust, relevance, completeness, closure, acceptance, integration, epoch completion, or replay correctness.

No implementation permission is granted yet.
