### ADV-053-A — same historical token, different declaration occurrences

Two different historical objects may both contain the token `NEXT_BUILD.md`. Historical `uniqueItems` prevents duplicates inside one source array, not equality across different objects.

Decision 019 already says `opaque_label` identity is the authored token **and its containing historical object**. That survives the attack. However, a future migration must preserve that occurrence identity. A mapping keyed only by token text would collapse two distinct historical declarations and could falsely apply one newly grounded typed target to both.

Required downstream guard: any future migration/link must identify the historical declaration occurrence strongly enough to distinguish its containing immutable object and field/role; token equality alone is not authority.

### ADV-053-B — composite pairing ambiguity

The proposal correctly says a source may have both a `locator` fact and an immutable `content_address` or `exact_axm_object` fact. But no typed representation exists yet.

A naive future shape such as parallel locator and digest arrays would allow hidden pairing by position, lexical order, resolver order, or recency. With locators L1/L2 and content addresses A/B, repository state alone would not say whether L1 is associated with A, B, both, or neither.

This does **not** require a fifth target identity class. It requires a future declaration/association rule: separate facts remain independent unless their association is explicitly represented.

### ADV-053-C / D — mutable locator and mirror cases

- same locator / different bytes must preserve both time/context observations without rewriting locator identity;
- same bytes / different locators must preserve distinct locator declarations without pretending content equality erases provenance/location facts.

The four-class proposal survives both because `locator` and immutable identity are orthogonal.

### ADV-053-E / F — exact/digest syntax without successful reproduction

Canonical-looking exact AXM syntax does not prove store availability or integrity. Digest syntax does not prove bytes exist. Mismatching bytes fail integrity. No logical-id, newest-version, resolver, location, or host fallback is justified.

The proposal already states this boundary; no contradiction reproduced.

### ADV-053-G / H — trust and closure laundering

Verified byte identity remains weaker than trust, relevance, correctness, sufficiency, or acceptance. Successful retrieval of every declared source remains weaker than completeness/closure. The proposal explicitly separates these states, so the attack does not require taxonomy repair.

### ADV-053-I — cross-field laundering

A source-looking `content_ref`, dependency ref, evidence ref, subject ref, or supersedes ref does not become source provenance by spelling. The proposal's field/relation boundary survives.

### ADV-053-J — conflicting parallel declarations

Two lanes/packets may make incompatible typed source declarations. Neither newest packet, schedule order, higher confidence, green CI, actor category, resolver preference, branch ownership, nor Git permission is a tie-breaker. Both remain facts until a later grounded policy resolves them.

The proposal explicitly preserves conflicts and therefore survives this attack.

### ADV-053-K — exact AXM object and content address covering equivalent bytes

Even when an AXM object's agreed byte scope happens to reproduce the same bytes named by a content address, target-class facts do not automatically collapse and no causal/provenance relation appears by equality alone. Any correlation must be explicit.

No fifth class is required.

## Downstream risk

The main downstream risk is **implicit association authority**. If Decision 020 defines target classes but not declaration occurrence/association, two independent facts can become coupled by storage order or resolver convention. That would reintroduce hidden state precisely where Institution Fabric is trying to make continuation explicit.

A second risk is **migration coalescing**: a globally keyed mapping from legacy token text to a typed target would silently rewrite distinct historical declarations that reused the same string.

Neither risk justifies changing the four target identity classes. Both are contract-shape risks for the next step.
