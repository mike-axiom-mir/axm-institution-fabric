### ADV-021-A — object-key ordering is host-language dependent unless specified

Observed repository behavior:

- `canonical_bytes()` calls Python `json.dumps(..., sort_keys=True, ensure_ascii=False)`;
- `IDENTITY_V0.md` says keys are sorted, but does not define the comparator.

Reproducible vector:

- key A: `U+E000` (``);
- key B: `U+10000` (`𐀀`).

Independent runtime witness executed during this activation:

```text
Python / Unicode scalar ordering:
{"":1,"𐀀":2}

JavaScript ordinary UTF-16 string ordering:
{"𐀀":2,"":1}
```

Why this matters: both implementations can honestly read the current repository prose as “sort object keys,” yet produce different canonical bytes and therefore different immutable SHA-256 identities. The Python implementation itself is deterministic; the continuity failure is that its ordering rule is not fully externalized from Python behavior.

Status: **observed exact-code portability counterexample**.

### ADV-022-A — `axmref:v1` percent encoding inherits a Python URL-encoder convention

Observed repository behavior:

- `_encode_component()` delegates to `urllib.parse.quote(value, safe="._-")`;
- `parse_immutable_ref()` treats the spelling produced by that helper as the canonical spelling;
- `IDENTITY_V0.md` says “canonical percent encoding” but does not define the exact raw/escaped character set or byte-level procedure.

Reproducible vector:

```text
component: a!b*a'b(c)

Python urllib.parse.quote(..., safe="._-"):
a%21b%2Aa%27b%28c%29

JavaScript encodeURIComponent:
a!b*a'b(c)
```

Both are common UTF-8 percent-encoding APIs. A future implementation using the second convention would construct a different reference for the same logical component, and the current parser would reject it as non-canonical.

Status: **observed exact-code portability/reconstructability counterexample**.
