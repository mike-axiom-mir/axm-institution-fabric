## Failure surface — ADV-049-J

### Expected boundary

The repository already froze a reusable proof-to-use transport rule in ADV-037: ordinary transport may fail closed, or it may preserve exact/named semantics; it must not silently change the meaning of an authoritative operational record.

Decision 016 introduces graph leaf records as `NamedTuple` types, including:

- `ExactPacketOutputNode`
- `ExactSamePacketDependencyEdge`
- `ExactStronglyConnectedComponent`

ADV-049-J directly tests one authoritative exact edge from a real end-to-end stored packet graph.

Acceptable outcomes are deliberately narrow:

1. ordinary stdlib JSON rejects the unsupported object; or
2. transport preserves named semantics exactly, e.g. the edge remains a mapping with `required_output_ref` and `dependent_output_ref`.

### Observed result

Python stdlib JSON accepted the authoritative `ExactSamePacketDependencyEdge` and decoded it as this positional list shape:

`[required_output_ref, dependent_output_ref]`

The native failure showed the real exact refs in that list and failed because the transported value was not a named mapping.

Therefore field meaning is preserved only by hidden knowledge of the originating Python class/tuple position. A replacement consumer receiving the ordinary JSON value cannot determine from the transported value itself which exact ref is `required_output_ref` and which is `dependent_output_ref` without reintroducing out-of-band implementation knowledge.

This is a proof-to-use continuity failure, not durable-store corruption and not an edge-selection failure.
