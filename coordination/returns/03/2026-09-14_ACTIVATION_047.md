## Repository behavior inspected directly

`FilesystemObjectStore.load()` / `load_bytes()` currently:

1. parse the exact immutable reference;
2. infer `<kind>.schema.json` when no schema is supplied;
3. derive one exact content-addressed path under the configured store root;
4. read only that path;
5. strict-parse and schema-validate the bytes;
6. reproduce canonical bytes;
7. reproduce the exact requested immutable reference;
8. fail rather than falling back by logical id, newest version, locator, recency, or store order.

The store exposes `ObjectNotFoundError`, `ObjectCorruptionError`, `ObjectReferenceMismatchError`, and generic `ObjectStoreError`.

One ordering detail matters for Decision 021 research: `_verify_existing()` attempts to read the exact path before schema validation. Therefore a Decision 020-valid reference whose kind is unsupported by the local runtime can produce `ObjectNotFoundError` when its path is absent before runtime schema support is ever exercised. That exception alone is not sufficient evidence to collapse `runtime capability` and `target availability` into one observation state.

A second continuity detail is structural rather than an implementation bug: `FilesystemObjectStore` is configured by a mutable filesystem root path. The root string is a location, not an immutable snapshot identity. The same textual root can yield different observations over time as exact objects are published or external state changes. A future observation result that records only the root path cannot truthfully claim replay of the original observation without a stronger bounded context identity or an explicit replay limitation.

## Observed findings

1. Canonical state clearly separates Decision 020 declaration validity from Decision 021 source observation.
2. The current exact store performs exact path lookup and exact identity reproduction without logical-id/newest/locator fallback.
3. The current store's failure classes already preserve useful distinctions between exact-path absence, corrupt bytes, reference/schema mismatch, and other store I/O failures.
4. Exact-path read occurs before schema validation inside `_verify_existing()`. Therefore an absent path can be observed before local schema support for the declared kind is tested.
5. The store root is represented as a filesystem `Path`, not an immutable snapshot/revision identity.
6. Decision 020 occurrence identity remains exact containing-object identity + declaration key; equal object refs do not erase that authored occurrence distinction.
7. PR #98 reinforces, without implementing Decision 021, that unsupported-current-runtime kind is not malformed declaration syntax.
8. No current repository evidence authorizes trust, provenance causality, completeness, closure, acceptance, Stage 5 integration, epochs, or replay from source observation success.

## Inferred findings — deliberately weaker than observed evidence

1. A future Decision 021/022 observation result should carry runtime capability standing separately from target availability, otherwise current store call ordering can make an unsupported-kind/absent-path case look indistinguishable from an ordinary supported-kind absence.
2. If a future projection wants replayable observation claims, `store_root` text alone is too weak as context identity. Either a stronger immutable/bounded store-context identity is needed, or the result must explicitly state the replay limitation.
3. Exact-load work may be safely deduplicated internally by exact object ref, but durable observation records still need declaration-occurrence attribution. Otherwise two authored declarations of the same target collapse and occupant replacement loses provenance of what was actually observed for which declaration.
4. Observation failures should be retained per targeted occurrence rather than filtered out, because disappearance destroys the distinction between `not observed` and `observed but unavailable/corrupt/unreadable/unsupported`.

These are research constraints for Lane 01, not a unilateral result-schema decision from Lane 03.

## Downstream risk

The highest continuity risks before an implementation decision opens are:

1. recording a mutable store path as though it were a replayable immutable context;
2. classifying a bare `ObjectNotFoundError` as context-free source nonexistence;
3. caching solely by `object_ref` and thereby losing declaration occurrence provenance;
4. dropping failed observation attempts and making uncertainty disappear;
5. letting one generic load-success field become integrity/trust/closure/acceptance authority;
6. reconciling contradictory parallel observations by newest-wins, actor identity, schedule order, CI, or Git state;
7. implicitly associating exact/content/locator declarations because they are adjacent or similarly named.
