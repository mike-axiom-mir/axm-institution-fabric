## Failure surface examined

Decision 010 requires a packet-created artifact's work-base provenance to identify the same exact immutable state revision as its exact claim base and its producer lane id to agree with the exact claim-base lane logical id.

Lane 03 attacked five ways this relation could become convincing-looking but non-reconstructable for a replacement occupant:

1. **ADV-043-A — structural exact-lookalike parser bypass**
   - Build an artifact whose v0.2 provenance ref is structurally accepted by the artifact schema but uses non-canonical percent-encoding (`%72` for unreserved `r`) in the logical-id component.
   - Oracle: the shared Stage 2 parser must still reject it before the relation can gain exact standing.

2. **ADV-043-B — corrupt exact provenance target**
   - Publish an exact state-revision target, construct a packet-created artifact that names it, then replace the stored target bytes so they no longer reproduce the requested immutable identity.
   - Oracle: operational exact-load must fail closed; an exact-looking ref string is not enough when its target cannot reproduce its identity.

3. **ADV-043-C — valid exact ancestor used as stale work base**
   - Construct an older exact revision and a later exact claim base whose `parent_revision_ref` names that older revision.
   - Point the created artifact provenance to the valid exact ancestor.
   - Oracle: ancestry is not equality. The older exact revision must still fail the created-output provenance precondition.

4. **ADV-043-D — packet array-order / partial-success laundering**
   - Put one correctly based created artifact and one stale-based created artifact in the same exact packet, each with exact subject-bound passing evidence.
   - Run both normal and reversed artifact/evidence array order.
   - Oracle: either order must fail on the stale artifact; one valid artifact or favorable array position cannot launder the packet-created provenance set.

5. **ADV-043-E — before/after same-logical-id storage decoys**
   - Store one same-logical-id/different-exact state revision before the authoritative base and another after it.
   - Point both claim and artifact to the authoritative exact ref.
   - Oracle: exact provenance remains bound to that authoritative ref; neither storage order nor a hypothetical newest/current interpretation may rebind it.
