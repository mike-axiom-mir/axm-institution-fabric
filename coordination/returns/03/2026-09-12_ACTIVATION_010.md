## Exact findings

### ADV-026-A — lifecycle schemas admit a noncanonical immutable-ref spelling

PR #15 uses this reference-language shape for each repaired base field:

```text
^axmref:v1:state-revision:(?:[A-Za-z0-9._~-]|%[0-9A-F]{2})+:(?:-|v=(?:[A-Za-z0-9._~-]|%[0-9A-F]{2})+):sha256:[0-9a-f]{64}$
```

Concrete witness:

```text
axmref:v1:state-revision:revision%2Efixture.0001:-:sha256:2222222222222222222222222222222222222222222222222222222222222222
```

The schema regex accepts `%2E`.

The integrated identity parser does not. `_decode_component()` decodes the component, re-encodes it with the Decision 003 canonical UTF-8/RFC3986-unreserved rule, and rejects the source unless the spelling round-trips exactly. `.` is unreserved and canonical encoding leaves it literal, so `revision%2Efixture.0001` is noncanonical.

`validate_instance()` validates the lifecycle object against JSON Schema but does not call `parse_immutable_ref()` for arbitrary nested reference strings.

Therefore the current contract permits a lifecycle object to be schema-valid and gain its own deterministic identity while embedding a base string that is not itself a valid canonical `axmref:v1` under the repository's identity layer.

**Observed:** exact schema and identity source disagree on accepted reference language.

**Inferred downstream failure:** code that treats schema validity as proof that `base_state_revision_ref` can be parsed/resolved may fail only after the lifecycle object has already been accepted or stored.

This is a concrete Decision 006 contract gap, not a request for a new architecture.

### ADV-027-A/B/C — exact base does not yet make logical member ids unique

Decision 006 intentionally left fields such as `lane_id`, `occupancy_id`, and `claim_id` logical unless evidence showed exact-instance ambiguity.

The concrete ambiguity now exists.

The integrated state-revision contract uses `uniqueItems` over exact-ref strings. It does **not** require uniqueness of the parsed logical id. The integrated membership tests themselves prove that two different lane objects may share the same logical lane id while producing different immutable refs.

A revision can therefore contain, for example:

```text
axmref:v1:lane:lane-02:-:sha256:aaaa...
axmref:v1:lane:lane-02:-:sha256:bbbb...
```

without violating `uniqueItems`, because the strings differ.

An occupancy against that exact base may still say only:

```text
lane_id = lane-02
```

and cannot prove which lane contract governs it.

The same relationship class exists for a work claim's logical `occupancy_id`, and later for logical claim/lane lookup used by packet/lifecycle processing.

This does **not** prove every logical id must become an exact ref. The smaller requirement is now explicit: before runtime dereferences one of these logical relationships, institutional validation must prove exactly-one resolution inside the relevant exact state, or the relationship must become exact. Recency, array order, mutable current state, or private chat cannot choose for it.

These are downstream Stage 4 semantic obligations, not a reason to widen PR #15 into a mass-ref rewrite.

## Root implications

### Truth

A field cannot truthfully be called a canonical immutable reference if the contract validator accepts spellings that the canonical reference parser rejects. CI success remains attached to the tests actually run; the new uncovered cases are not silently called tested.

### Agency / non-domination

A later occupant must not have to guess which same-named lane/occupancy/claim instance a logical id meant. No recency rule, array order, current state, actor identity, or hidden conversation may become undeclared authority over that choice.

### Continuity

PR #15 substantially improves continuity by binding the lifecycle base itself to an exact state. `ADV-026-A` must be closed so that exactness survives validation into resolution, and `ADV-027-*` preserves the next concrete requirement for reconstructing relationships inside that exact state.

### Wisdom before speed

Do not widen this repair into integration/epoch/replay or a universal id rewrite. Repair the exact reference-language mismatch now because it is directly in the active gate; carry logical-member uniqueness forward as a bounded Stage 4 obligation. Do not build a schema-history registry solely for repository history that does not yet exist, while keeping `ADV-025-A` explicit before real incompatible persisted history appears.

## Unresolved uncertainty

1. The smallest implementation for `ADV-026-A` is not prescribed here. Lane 02 may tighten the state-revision-ref grammar, add a validator that delegates to `parse_immutable_ref`, or choose another deterministic mechanism as long as contract acceptance and identity-parser acceptance become equivalent for this field.
2. The same weak regex family already appears in integrated exact-membership schemas. Repairing `ADV-026-A` may reveal a shared validation primitive rather than a PR #15-only patch; Lane 01/Lane 02 should keep that scope evidence-driven.
3. `ADV-027-*` representation remains deliberately open: exact refs are one option, but exact-base-local uniqueness validation may be smaller and preserve logical navigation ids.
4. External/local/uncommitted object stores are not visible in repository evidence, so `ADV-025-A` cannot be globally cleared.
5. Existing `ADV-024-A`, `ADV-002-C`, integration-receipt, epoch, cross-language identity, power-loss, writer-concurrency, and filesystem-portability boundaries remain unchanged.

## Downstream risk

If `ADV-026-A` is ignored, a future work ledger may persist a schema-valid lifecycle object whose claimed base cannot be parsed by the same identity layer used for exact lookup. Failure would appear later and could be misdiagnosed as missing history rather than invalid institutional state.

If `ADV-027-*` is ignored when Stage 4 begins dereferencing logical relationships, an exact base may still contain multiple same-named candidate members and a replacement occupant could continue the wrong lane/occupancy/claim history while every involved object remains individually valid.
