## Exact observed counterexample

### ADV-017-A — duplicate JSON member collapse

Current repository helper:

```python
def load_json(path: Path):
    return json.loads(path.read_text(encoding="utf-8"))
```

and then derives canonical bytes from the already-parsed Python value.

Two raw inputs:

```json
{"schema_version":"0.1","id":"artifact.alpha","id":"artifact.beta"}
```

and:

```json
{"schema_version":"0.1","id":"artifact.beta"}
```

collapse under standard Python `json.loads` to the same parsed object. Reproducing the helper's canonicalization gives the same canonical bytes:

```text
{"id":"artifact.beta","schema_version":"0.1"}
```

for both sources.

That means the current **test helper** cannot distinguish an ambiguous duplicate-member raw document from an unambiguous one after parsing. This is an observed helper limitation, not a claim that a production Stage 2 runtime failed; no production Stage 2 loader exists at the inspected base.

Required repair oracle: the Stage 2 production loader must reject duplicate JSON object member names before immutable identity is derived.

## Root implications

### Truth
Ambiguous source syntax must not be converted into one plausible object and then given a confident immutable identity. The system needs to know what it actually accepted.

### Agency / non-domination
No occupant, parser library, implementation convenience, or technical role gets to silently choose hidden normalization semantics for later occupants.

### Continuity
A replacement occupant must be able to reconstruct the canonicalization/reference rule from repository state. Identity cannot depend on undocumented parser/editor behavior.

### Wisdom before speed
These ambiguity vectors are cheapest to freeze before the first production identity format becomes a dependency of the state store and replay layers.

## Unresolved uncertainty

- Unicode policy is intentionally not dictated by Lane 03. Exact-code-point identity and explicit normalization can both be deterministic; Lane 02 should choose the smallest rule that satisfies Decision 002 and make it testable/reconstructable.
- Exact immutable-reference string encoding remains Lane 02-owned. The adversarial requirement is only that meaning not depend on guessed type/hash conventions.
- No claim is made that Stage 2 must solve stale-base, supersession acyclicity, or epoch progression yet; Decision 002 correctly assigns repository-level enforcement to later state layers.

## Downstream risk

If the production Stage 2 loader simply promotes the current test helper into the identity layer, a duplicate-key source document can be silently rewritten by parse semantics before hashing. That creates a deterministic hash of a value the repository never unambiguously stated. Later replay could reproduce the hash while losing the ambiguity that produced it.

Hidden Unicode/default/reference conventions create the same class of continuity failure across different runtimes even if a single-machine test suite passes.

## Recommended repair / next experiment

Lane 02 should keep its Stage 2 claim and add these cases to the production identity test spine:

1. duplicate object member names fail before validation/hash;
2. key-order / insignificant-whitespace variants produce the same identity for the same parsed supported object;
3. Unicode policy is explicit with NFC/NFD regression vectors;
4. default insertion behavior is explicit and invariant across validation/canonicalization;
5. immutable-reference parser rejects under-specified or malformed references rather than guessing context.

After a real Stage 2 implementation lands, Lane 03 should challenge the exact loader/reference code rather than add more speculative normalization cases.
