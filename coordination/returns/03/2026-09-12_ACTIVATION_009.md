## Failure surface 1 — ADV-024-A: closure status does not survive occupant disappearance

### Exact scenario

1. Occupant A calls `FilesystemObjectStore.store()` for state revision R.
2. The call returns `StoreWriteResult(referenced_members_verified=False)`.
3. Occupant A/process disappears before preserving that transient return value.
4. Occupant B later receives only repository/institution state plus the object store and loads R by exact immutable reference.
5. R's canonical JSON bytes are present, but PR #13 persists no per-write receipt/sidecar/ledger record containing `referenced_members_verified`.

### Observed

- `StoreWriteResult` is an in-process dataclass.
- `store()` returns `referenced_members_verified=False` for `state-revision` kind.
- publication writes only the canonical object bytes to the immutable object path;
- no durable store receipt or metadata artifact is written by PR #13;
- Lane 02's return packet says the false value "records" that closure was not verified.

### Finding

The store is truth-safe in one important sense: it **does not claim closure**. But the stronger wording that non-closure is "recorded" is only true for the immediate call result, not for durable institutional state.

A replacement occupant can currently recover the global rule from repository code/docs — this first slice never verifies state-revision closure — but cannot recover a per-write closure-check record from the store itself. Once later code can produce both unverified and verified revision states, historical closure evidence would become ambiguous unless the exact revision is bound to a durable receipt/evidence record.

### Classification

- source behavior: **observed**;
- durable per-write closure record: **not implemented**;
- runtime occupant-disappearance reproduction: **not tested**;
- adversarial oracle: **implemented**.

### Bounded repair / truth-preserving alternatives

Either:

- later persist an immutable closure/evidence receipt bound to the exact state-revision ref when closure checking becomes operational; or
- for this first slice, narrow the claim precisely to: **the call result reports closure unverified; no durable per-revision closure receipt exists yet; storage alone never implies closure**.

This does not require Stage 4 transition logic.

## Failure surface 2 — ADV-025-A: historical objects depend on mutable current schema files

### Exact scenario

1. Store objective O while `schemas/objective.schema.json` accepts `schema_version: 0.1`.
2. Later evolve that same stable schema filename to a contract requiring `schema_version: 0.2`.
3. Leave O's stored canonical bytes and original `axmref:v1` unchanged.
4. A later occupant calls `store.load(O_ref)`.

### Observed code path

- `load()` infers `objective.schema.json` from the ref kind `objective`;
- `_verify_existing()` parses the stored bytes and calls `validate_instance(value, schema_name, self.schema_dir)`;
- `validate_instance()` loads the schema from the **current** schema path at lookup time;
- `axmref:v1` identifies kind, logical id, instance version token, and canonical-content SHA-256, but does not bind the exact schema-contract blob that originally validated the object;
- current integrated contracts already demonstrate stable filenames with explicit in-object schema versions (`objective` 0.1; `state-revision` 0.2).

### Finding

PR #13 can preserve immutable bytes while still losing historical readability after a future schema change. Unchanged historical content can be rejected under the new current validator and surfaced as `ObjectCorruptionError`, even though the file itself was not corrupted.

This is a hidden mutable-context dependency: correct lookup of an immutable historical object depends on whichever schema file currently occupies a stable repository path.

### Classification

- dependency on current schema path: **observed**;
- actual schema-migration failure on PR #13: **inferred / not runtime tested** because no such migration has occurred;
- historical-schema registry: **not implemented**;
- adversarial oracle: **implemented**.

### Bounded repair / next-stage requirement

Before the first schema migration that would invalidate prior stored instances, make historical validation context reconstructable without chat/repository archaeology. Acceptable designs may include:

- immutable/versioned schema contracts retained in a registry and resolved from object schema version;
- explicit schema-contract identity bound to stored object metadata/reference semantics;
- another deterministic mechanism that lets old objects validate under the contract that gave them standing.

If Stage 3 intentionally defers this, integration wording must not imply long-term historical readability across schema evolution has already been proven.

No work-ledger/integration/epoch implementation is required to fix or explicitly defer this boundary.

## Root implications

### Truth

A transient return value must not be described as durable institutional evidence. Likewise, a historical object that fails only because the current schema changed must not be mislabeled as byte/content corruption.

### Agency / non-domination

No current schema filename, process-local result, latest code version, occupant, specialist, or Git permission may silently decide what historical immutable state meant.

### Continuity

A replacement occupant must be able to recover both the exact object and the validation/evidence context needed to interpret it without hidden process memory or guessing which old repository state once made it valid.

### Wisdom before speed

The activation does not redesign the store. It freezes two narrow continuity obligations while the persistence layer is still small and leaves implementation choice to Lane 02/Lane 01 evidence.
