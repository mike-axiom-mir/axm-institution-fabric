## Failure surface examined

The audit used the Decision 002 distinction between logical identity and immutable instance identity plus Decision 005's same-logical-id/different-content revision witness.

Concrete adversarial setup:

- immutable state revision A and immutable state revision B both carry logical `id = revision.same-logical-id`;
- A and B have different canonical bytes and therefore different `axmref:v1:state-revision` references;
- any consequential relationship that stores only `revision.same-logical-id` cannot prove whether it means A or B.

### 4. Integration and epoch replay also have exact packet-instance obligations

`integration-receipt.packet_ids` and `epoch.packet_ids` are logical ids. Because return packets are canonical objects whose content can differ while a logical id is reused, replay of an integration decision or epoch membership cannot safely choose an instance by name/recency/private memory.

These edges require exact return-packet instance semantics before Stage 5/6 replay claims.

### 5. Epoch lane identity needs exact semantics, but not necessarily a blind field rename

`epoch.lane_ids` may remain logical only if the exact epoch base revision plus an explicit machine-checkable uniqueness/resolution rule identifies exactly one lane instance for each id. Otherwise the epoch should store exact lane refs.

This is intentionally **not** a recommendation to mass-convert every `*_id` field.

### 6. Selective stale compatibility needs target-instance evidence

An exact `return-packet.base_state_revision` is necessary but may not be sufficient if later integration permits multiple packets from a shared epoch base after unrelated state has advanced.

For `artifacts_modified`, the integrator must either:

- deterministically derive the exact target instance observed in the packet's exact base revision under an explicit uniqueness rule; or
- record an expected prior immutable target ref.

Otherwise selective conflict detection can silently apply work to a target version the packet never saw.

## Root implications

### Truth

A logical revision or packet name cannot establish which immutable instance actually participated in a consequential transition when more than one valid instance can share that logical name.

### Agency / non-domination

No founder, specialist, model, scheduler, Git permission, or recency heuristic may silently choose which ambiguous instance a relationship meant.

### Continuity

A replacement occupant must reconstruct the exact state entered, worked from, returned from, integrated from/to, and compared in an epoch without private conversation or hidden mutable-id convention.

### Wisdom before speed

The audit does not demand a repository-wide id rewrite or pull Stage 5/6 runtime forward. It freezes exact obligations now and assigns them to the stage where each relationship becomes operational.
