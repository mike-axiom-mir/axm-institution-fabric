## Exact scenarios / counterexamples exercised

### 1. Later same-id occupancy cannot rebind an existing claim

Sequence:

```text
base N stored
occupancy O-A created from N, logical id = occupancy.same
claim C binds exact ref(O-A)
occupancy O-B later stored, same logical id, different immutable content/ref
reload C
```

Observed: `C.occupancy_ref` remains exactly `ref(O-A)`. Loading that exact ref returns occupant A. O-B does not substitute through recency or logical-id equality.

### 2. Later same-id claim cannot rebind an existing return packet

Sequence:

```text
base N stored
occupancy O stored
claim C-A stored, logical id = claim.same
packet P binds exact ref(C-A)
claim C-B later stored, same logical id, different immutable content/ref
reload P
```

Observed: `P.claim_ref` remains exactly `ref(C-A)` and exact loading returns C-A, not later C-B.

### 3. Same-id occupancy already present in the work base cannot override the post-base target

Sequence:

```text
prior revision -> old occupancy O-old, logical id occupancy.same
work base N includes exact ref(O-old)
new occupancy O-new is created after N with same logical id
claim C against N binds exact ref(O-new)
```

Observed: C preserves `ref(O-new)` even though N already contains another exact occupancy with the same logical id. The base-local old object is not silently preferred.

This directly challenges an easy implementation mistake: reusing the exact-base logical resolver for a relationship that Decision 007 classifies as created-after-base.

### 4. Same-id claim already present in the work base cannot override the post-base target

Sequence mirrors scenario 3:

```text
prior revision -> old claim C-old, logical id claim.same
work base N includes exact ref(C-old)
new claim C-new is created after N with same logical id
packet P against N binds exact ref(C-new)
```

Observed: P preserves `ref(C-new)`. The older same-id claim already present in N does not substitute.

### 5. Wrong-kind and trailing-data refs fail through normal store publication

The adversarial test routes these through `FilesystemObjectStore.store(...)`, not isolated regex checks:

- objective ref placed in `work-claim.occupancy_ref`;
- occupancy ref placed in `return-packet.claim_ref`;
- otherwise canonical occupancy ref plus final LF;
- otherwise canonical work-claim ref plus trailing `x`.

Observed: all cases fail with `ContractValidationError` before any `.json` object is published.

### 6. Exact reference syntax is not target existence

A work claim with a canonical, typed, parser-valid occupancy ref whose target is deliberately absent can itself still be validated and immutably stored. Loading that exact missing occupancy ref then fails explicitly with `ObjectNotFoundError`.

Observed conclusion:

```text
referring object publication
    != referenced target existence
    != relationship closure
```

This is consistent with PR #24's declared truth boundary rather than a contradiction of it.

I freeze this as **ADV-031-A — lifecycle authoritative-target verification**:

> Before a future lifecycle transition treats `work-claim.occupancy_ref` or `return-packet.claim_ref` as an operationally valid relationship, it must exact-load and identity-verify the supplied target ref (and then enforce whatever relation-specific semantics that transition actually requires). Merely persisting the referring object is insufficient evidence that the target exists.

`ADV-031-A` is a Stage 4 runtime obligation, not a blocker on PR #24's bounded contract/identity repair, because PR #24 explicitly does not claim target-existence closure.

## Root implications

### Truth

The exact historical object named by a work claim or return packet survives later same-logical-id objects and same-id objects already present in the base. The activation also preserves the distinction between a valid reference spelling and verified target existence.

### Agency / non-domination

No newest/current selector, storage order, base-array membership, actor identity, schedule position, founder status, confidence, or Git permission acquires hidden authority over which post-base immutable object a historical relationship means.

### Continuity

A replacement occupant can recover the same exact target identity from the persisted claim/packet without private chat memory. When the target is missing, the failure is explicit rather than silently redirected to another same-id object.

### Wisdom before speed

No lifecycle mutation was pulled forward. The test branch stays adversarial/evidence-only and records target verification as a later runtime obligation rather than expanding PR #24 into a closure engine.
