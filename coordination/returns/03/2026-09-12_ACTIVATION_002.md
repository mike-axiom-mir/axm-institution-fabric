## Observed findings

These are **observed schema-permissiveness findings by direct contract inspection**, not runtime integration failures:

### 1. Strong evidence state can be weakly supported

`evidence-record.schema.json` requires `schema_version`, `id`, `subject_ref`, `state`, and `claim`, but `method` and `source_refs` remain optional for every evidence state. Therefore an object may structurally claim `automated_tested` without preserving how or from where that evidence was produced.

Continuity risk: a replacement occupant can see the label but may be unable to reconstruct the evidence basis.

### 2. Root conflict is not coupled to acceptance

`integration-receipt.schema.json` independently validates `decision` and the four `root_grounding` assessments. It does not currently prevent `decision: accepted` from coexisting with a root assessment of `conflict`.

This is not a claim that every root uncertainty must automatically block all integration. It is a narrower finding: **explicit constitutional conflict and canonical acceptance currently have no defined machine-readable relationship**.

### 3. Decision and revision effect can contradict

`integration-receipt.schema.json` allows `resulting_state_revision` to be null or string regardless of decision. Thus `deferred` / `rejected` / `repair_requested` can structurally produce a new revision, while `accepted` can structurally produce no revision.

Continuity/replay risk: later occupants cannot infer the state-transition meaning from the receipt without hidden convention.

### 4. Occupancy lifecycle can contradict itself

`occupancy.schema.json` independently validates `status` and `ended_at`. An occupancy can be `active` with a non-null end timestamp, or `ended` without a concrete end timestamp.

Continuity risk: occupant replacement and abandoned-claim recovery can become dependent on unstored convention.

## Root implications

- **Truth:** a strong evidence label without reconstructable support risks becoming a truth-state decoration rather than evidence.
- **Agency / non-domination:** an explicit root conflict must not be silently overridden by role, actor, Git permission, or convenience; the machine-readable transition semantics must say what happened and why.
- **Continuity:** contradictory occupancy lifecycle or receipt state forces the next occupant to guess hidden convention.
- **Wisdom before speed:** cross-field semantics should be resolved before Stage 1 contracts are treated as frozen, while the change surface is still small.

## Unresolved uncertainty / dissent

- Whether `uncertain` root assessments may coexist with `accepted` or `partially_integrated` is an institutional semantic question and should be reviewed by Lane 01; Lane 03 does not silently decide it.
- Whether every high evidence state requires both `method` and at least one `source_ref` may be too strict for some future evidence types. The invariant is reconstructable support, not a specific field shape.
- Recovery may need a future occupancy status such as abandoned/expired/interrupted; this activation does not prescribe the status vocabulary.

## Downstream risk

If these contradictions are frozen into the contract pack, later runtime code can be internally deterministic while still reconstructing ambiguous institutional truth. That would satisfy serialization tests but weaken the actual continuity proof.

## Recommended repair / next experiment

Lane 02 should add cross-field contract tests before Stage 1 is called complete:

1. strong evidence states require reconstructable support;
2. accepted integration cannot silently coexist with explicit constitutional root conflict;
3. integration decision and resulting revision presence are coherent;
4. occupancy status and end-state fields are coherent.

Lane 01 should decide only the semantic point that is genuinely constitutional: the allowed relationship between root assessments (`grounded` / `uncertain` / `conflict`) and integration decisions. The technical encoding remains Lane 02 territory.

After repair, Lane 03 should rerun these exact four counterexamples and then move to stale-base and provenance-version challenges at the cross-object/runtime layer.
