## Observed finding — ADV-030-A

### Scenario

Use this exact `objective_ref`:

```text
axmref:v1:objective:%FF:-:sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

A corresponding version-component witness also exists:

```text
axmref:v1:objective:member:v=%FF:sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

### Observed contract behavior

PR #19's repaired component regex allows uppercase percent triplets except triplets that encode RFC3986-unreserved ASCII bytes. `%FF` is therefore accepted by the regex.

The same component grammar is used by all nine affected state-revision member field families.

### Observed Stage 2 parser behavior

`parse_immutable_ref()` delegates each encoded component to `_decode_component()`. `_decode_component()` reconstructs bytes from percent triplets and decodes with strict UTF-8.

Byte `0xFF` is not a valid UTF-8 start byte. The reference is therefore rejected by the canonical parser.

### Result

**Concrete schema/parser discontinuity remains.**

A state-revision member string can satisfy the repaired PR #19 schema language while failing canonical Stage 2 reference parsing.

## Observed finding — ADV-030-B

### Scenario

Use this exact `objective_ref`:

```text
axmref:v1:objective:e%CC%81:-:sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

`e%CC%81` decodes to `e` followed by combining acute accent `U+0301`.

Its NFC-equivalent component is `é` (`U+00E9`), canonically percent-encoded as `%C3%A9`.

A corresponding non-NFC version-component witness also exists:

```text
axmref:v1:objective:member:v=e%CC%81:sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

### Observed contract behavior

PR #19's regex accepts `%CC` and `%81`: neither triplet is a percent-encoding of an ASCII unreserved byte, and the reference satisfies the true end assertion.

### Observed Stage 2 parser behavior

After UTF-8 decoding, `_decode_component()` calls `_assert_canonical_subset()`. Stage 2 rejects text when `unicodedata.normalize("NFC", value) != value`.

The decomposed `e + U+0301` string is therefore rejected even though the state-revision schema accepts the percent spelling.

### Result

**A second concrete schema/parser discontinuity remains.**

The repaired regex still does not encode the Stage 2 NFC invariant.

## Root implications

### Truth

A string cannot truthfully be treated as an exact canonical immutable reference by the state-revision contract if the canonical reference parser rejects the same bytes.

### Agency / non-domination

A replacement occupant must not depend on hidden cleanup, Unicode normalization, or implementation-specific reinterpretation to decide what an exact reference meant.

### Continuity

## Uncertainty preserved

This activation does **not** prove that invalid UTF-8 and non-NFC are the only remaining schema/parser discontinuities.

PR #19 itself correctly records that its regex regressions are not a mathematical proof of full language equivalence with `parse_immutable_ref()`.

The deeper architectural question is whether exact reference semantics should continue to be duplicated in increasingly complex JSON-Schema regexes or whether contract validation should reuse the canonical parser as the single semantic source of truth. Lane 03 records that as a repair-shape recommendation, not a unilateral architecture decision.

## Downstream risk

That would force a future occupant/runtime to invent cleanup or rejection policy after the object already entered canonical storage/state, recreating the hidden-convention problem the Building is intended to remove.
