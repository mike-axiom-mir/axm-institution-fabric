## Behavior implemented

Added `resolve_return_packet_evidence_subjects(...)` in `axm_institution/packet_evidence_subject.py`.

The resolver:

1. begins from canonical `resolve_return_packet_output_identity(...)`, so exact packet/artifact/evidence selection, proof-to-use/materialization invariants, and the existing `artifacts_modified` fail-closed boundary are inherited rather than reimplemented;
2. offers every exact-loaded evidence record's `subject_ref` to the shared Stage 2 `parse_immutable_ref(...)` parser;
3. treats a non-exact subject string as explicit unmatched evidence with reason `non_exact_subject`; it receives no standing from output type, evidence state, logical id, path spelling, array order, storage order, recency, actor identity, or hidden history;
4. requires a syntactically exact subject used for this created-artifact precondition to have kind `artifact`; a wrong-kind exact subject fails closed with `EvidenceSubjectKindError`;
5. binds evidence only when the full canonical subject ref exactly equals one of the packet's already-grounded `artifacts_created[]` refs;
6. exposes an exact artifact subject that is not one of the packet-created exact refs as explicit unmatched evidence with reason `exact_artifact_not_created_by_packet`;
7. intentionally ignores `artifact.evidence_refs` as post-artifact compatibility authority under Decision 008;
8. remains read-only and does not mutate packet, artifact, evidence, claim, occupancy, or revision state.

The returned result preserves the already-grounded output-identity result, one evidence tuple per exact created artifact, and explicit unmatched evidence records/reasons. It is not an acceptance or compatibility verdict.

## Uncertainty / truth boundary

This implementation establishes only exact subject grouping for packet-created artifacts.

It does not establish that a bound evidence state is sufficient for a lane output, that multiple evidence records combine conjunctively or alternatively, that evidence method/source quality is adequate, that an artifact's own `evidence_refs` is historically authoritative, or that the packet is acceptable/canonical.

A non-exact `subject_ref` remains a valid evidence-schema value and may be meaningful for another future relationship. This resolver merely refuses to treat it as proof for an exact packet-created artifact under Decision 008.

The resolver does not exact-load the evidence subject again because packet-created artifacts were already exact-loaded and verified by the canonical output-identity resolver; binding is equality against those exact canonical refs, not a second selection path.

Full cross-language behavior remains untested. Filesystem power-loss durability, concurrent-writer stress, and non-Linux atomic-publication behavior remain outside this slice.

## Root grounding

### Truth

Evidence is associated with a created output only from an explicit exact subject ref. Same-logical-id substitution, unrelated passing evidence, and contradictory artifact-side hints cannot be silently relabeled as support for another output.

### Agency / non-domination

Output type coincidence, evidence state, recency, array/storage order, actor identity, specialist title, schedule position, private chat memory, and Git permission gain no authority to assign an evidence record to an artifact.

### Continuity

A later occupant can reconstruct the demonstrated evidence-to-output relationship from explicit immutable refs and repository code/tests rather than hidden intent or Python object history.

### Wisdom before speed

The implementation stops at the exact subject precondition. It does not opportunistically decide required-state or compatibility semantics simply because enough plumbing now exists to do so.
